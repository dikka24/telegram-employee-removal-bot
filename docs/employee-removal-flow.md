# Flow: проверка сотрудников, удаление из групп и алерты

Документ описывает рабочий flow Telegram-бота для:

- подключения и отслеживания управляемых групп;
- автоматического удаления сотрудников по статусу из Google Sheets;
- ручного удаления сотрудника по корпоративной почте;
- поиска пользователей, которые не прошли регистрацию;
- отправки алерта в ту же группу, где такие пользователи были замечены.

## Основные источники данных

### Google Sheets: `HQ E - COM`

Лист `HQ E - COM` является основным источником сотрудников.

Бот использует поля:

- `ФИО` - имя сотрудника;
- `Почта` - корпоративная почта;
- `Статус` - статус сотрудника;
- `ТГ` - Telegram ID сотрудника.

Если все строки с одним и тем же `ТГ` имеют статус из `DELETE_STATUSES`, сотрудник считается кандидатом на удаление из управляемых групп.

### Google Sheets: `Registration`

Лист `Registration` хранит успешные регистрации через бота:

- `full_name`;
- `email`;
- `telegram_id`;
- `username`;
- `registered_at`.

Лист используется в flow алертов по незарегистрированным пользователям, чтобы не считать уже зарегистрированных людей неизвестными.

### Google Sheets: `Список Диёр`

Лист `Список Диёр` используется как дополнительный список известных Telegram ID для flow алертов.

Бот читает Telegram ID из колонки `E`.

### Локальная БД SQLite

Бот хранит служебные данные локально:

- `managed_chats` - группы, где бот был активирован или проигнорирован;
- `chat_members` - локальный индекс участников групп;
- `observed_chat_users` - пользователи, замеченные в approved-группах;
- `deletion_log` - история попыток удаления.

## Подключение и отслеживание групп

1. Боту выдают права администратора в группе.
2. Бот получает событие `my_chat_member`.
3. Бот отправляет администраторам запрос: активировать работу в этой группе или нет.
4. Администратор выбирает:
   - `Да` - группа сохраняется как `approved`;
   - `Нет` - группа сохраняется как `ignored`.
5. Если группа approved, бот проверяет свои права:
   - если права достаточные, группа становится `approved + active`;
   - если прав недостаточно, группа остается `approved`, но `inactive`.
6. По расписанию запускается healthcheck:
   - бот повторно проверяет approved-группы;
   - обновляет признак `active`;
   - inactive-группа может стать active после исправления прав.

## Отслеживание пользователей в группах

В approved-группах бот наблюдает активность пользователей:

- обычные сообщения;
- новых участников;
- нажатия callback-кнопок.

Если пользователь не бот и группа approved, бот сохраняет его в `observed_chat_users`:

- `chat_id`;
- `user_id`;
- `username`;
- `full_name`;
- время первого и последнего наблюдения.

Эти данные используются для поиска людей, которые находятся в группе, но не зарегистрированы как сотрудники.

## Автоматическое удаление по статусу

Автоматическая проверка запускается по расписанию `STATUS_SCAN_INTERVAL_MIN`.

Flow:

1. Бот читает лист `HQ E - COM`.
2. Бот группирует строки по Telegram ID из колонки `ТГ`.
3. Если у строки нет Telegram ID, она не участвует в автоудалении.
4. Для каждого Telegram ID бот проверяет все строки с этим ID.
5. Если все статусы по этому Telegram ID входят в `DELETE_STATUSES`, пользователь становится кандидатом на удаление.
6. Если хотя бы одна строка по этому Telegram ID имеет другой статус, пользователь не удаляется.
7. Если Telegram ID входит в `ADMIN_IDS`, пользователь пропускается.
8. Бот получает список approved-групп.
9. Для каждой группы бот пытается удалить пользователя.
10. Количество попыток ограничивается `MAX_KICKS_PER_STATUS_RUN`.

Пример:

| Telegram ID | Статусы | Результат |
|---:|---|---|
| `123` | `УДАЛИТЬ` + `ОСТАВИТЬ` | Не удалять |
| `123` | `УДАЛИТЬ` + `УДАЛИТЬ` | Удалять |

## Ручное удаление по email

Ручное удаление запускается из админ-панели.

Flow:

1. Админ открывает `/admin`.
2. Выбирает `Ручное удаление по почте`.
3. Вводит корпоративную почту сотрудника.
4. Бот валидирует email.
5. Бот ищет сотрудника в `HQ E - COM` по email.
6. Если `telegram_id` не найден, бот сообщает об ошибке.
7. Если `telegram_id` найден, бот проходит по approved-группам и пытается удалить пользователя.
8. После завершения бот отправляет админу Excel-отчет и итог:
   - email;
   - Telegram ID;
   - сколько удалений выполнено;
   - сколько ошибок произошло.

## Механика удаления из группы

Для удаления пользователя бот использует два Telegram API вызова:

1. `ban_chat_member(chat_id, telegram_id)`
2. `unban_chat_member(chat_id, telegram_id)`

Так пользователь удаляется из группы, но не остается в постоянном бане.

Возможные результаты:

- `kicked` - пользователь удален;
- `error` - Telegram API вернул другую ошибку.

Если Telegram сообщает, что пользователя уже нет в группе, бот пишет `result = kicked`, а в `reason` указывает `already_not_member`. Это считается успешным результатом.

После успешного удаления бот:

- удаляет пользователя из локального индекса `chat_members`;
- пишет результат в `deletion_log`.

## Алерты по незарегистрированным пользователям

Проверка незарегистрированных пользователей запускается по расписанию `UNKNOWN_SCAN_INTERVAL_HOURS`.

Flow:

1. Бот читает лист `HQ E - COM`.
2. Собирает список известных Telegram ID:
   - `HQ E - COM`, колонка `ТГ`;
   - `Registration`, колонка `telegram_id`;
   - `Список Диёр`, колонка `E`;
   - `ADMIN_IDS`.
3. Бот проходит по всем `approved + active` группам.
4. Для каждой группы берет последних пользователей из `observed_chat_users`.
5. Сравнивает `user_id` с известными Telegram ID.
6. Если пользователь не найден в известных источниках, он считается незарегистрированным.
7. Бот проверяет, можно ли снова отправлять алерт по этому пользователю.
8. Если алерт можно отправить, бот формирует сообщение со списком упоминаний.
9. Бот отправляет сообщение в ту же группу, где пользователи были замечены.
10. После успешной отправки бот обновляет `last_alerted_at`.
11. Старые наблюдения удаляются по `UNKNOWN_USER_RETENTION_DAYS`.

Пример смысла алерта:

> Обнаружены пользователи, которые не прошли регистрацию в @uzum_administration_bot.
> Проверьте участников и при необходимости удалите их из группы.
