# Telegram HR Access Bot: функциональное описание для DPO и ИБ

Дата актуализации: 2026-07-14  
Контур: production, VM `vm-telegram-hr-01`  
Бот: `@uzum_administration_bot`

## 1. Назначение

Telegram HR Access Bot автоматизирует контроль доступа сотрудников к корпоративным Telegram-группам.

Основные задачи:

- регистрация сотрудника через корпоративную почту и OTP-код;
- фиксация успешной регистрации в Google Sheets;
- подключение Telegram-групп к управлению только после подтверждения администраторами;
- автоматическое удаление сотрудников из approved-групп по статусу в HR-таблице;
- ручное удаление сотрудника администратором по корпоративной почте;
- выявление пользователей в approved-группах, которые не прошли регистрацию;
- ежедневная отправка алерта о незарегистрированных пользователях в ту же группу;
- контроль работоспособности polling-процесса и автоматический рестарт контейнера при сбое.

Бот не предназначен для чтения, анализа или хранения содержимого переписки.

## 2. Компоненты системы

| Компонент | Назначение |
|---|---|
| Telegram Bot API | Получение событий, отправка сообщений, удаление пользователей из групп |
| Python / aiogram | Основная логика бота и обработчики команд |
| APScheduler | Периодические задачи: удаление, healthcheck групп, алерты |
| Google Sheets API | Чтение HR-таблиц и запись регистраций |
| SMTP | Отправка OTP-кода на корпоративную почту |
| SQLite | Локальное хранение служебных данных бота |
| Docker Compose | Запуск сервиса `bot` |
| Cron watchdog | Проверка polling через `getUpdates` и рестарт контейнера при сбое |

Сервис запускается в Docker-контейнере командой `python -m app.main`.

## 3. Роли и доступы

| Роль | Возможности |
|---|---|
| Обычный пользователь | Запустить `/start`, пройти регистрацию через корпоративную почту и OTP |
| Администратор бота | Открыть `/admin`, выполнить ручное удаление по email, получить список групп, approve/ignore новых групп |
| Сервисный аккаунт Google | Читать и обновлять Google Sheets в рамках выданных прав |
| Telegram bot | Получать события из Telegram, отправлять сообщения, удалять участников при наличии прав администратора группы |

Доступ к административным функциям ограничен списком `ADMIN_IDS` в конфигурации.

## 4. Источники данных

### 4.1. Google Sheets: `HQ E - COM`

Основной лист сотрудников.

Используемые колонки:

| Колонка | Назначение |
|---|---|
| `ФИО` | Имя сотрудника |
| `Почта` | Корпоративная почта |
| `Статус` | Статус сотрудника для логики удаления |
| `ТГ` | Telegram ID сотрудника |

В production статус для удаления: `УДАЛИТЬ`.

### 4.2. Google Sheets: `Registration`

Лист успешных регистраций через бота.

Используемые колонки:

| Колонка | Назначение |
|---|---|
| `full_name` | Имя Telegram-пользователя на момент регистрации |
| `email` | Корпоративная почта, подтвержденная OTP |
| `telegram_id` | Telegram ID пользователя |
| `username` | Telegram username, если есть |
| `registered_at` | Время регистрации в UTC |

При повторной регистрации с той же почтой строка обновляется по email.

### 4.3. Google Sheets: `Список Диёр`

Дополнительный лист исключений/известных пользователей для daily alert по незарегистрированным.

Используемая колонка:

| Колонка | Назначение |
|---|---|
| `E` | Telegram ID, которые считаются известными и не должны попадать в алерт неизвестных пользователей |

Этот лист используется только в flow поиска незарегистрированных пользователей в группах.

### 4.4. Конфигурация `.env`

Конфигурация хранит технические параметры и секреты.

Основные параметры без раскрытия секретных значений:

| Параметр | Назначение |
|---|---|
| `BOT_TOKEN` | Токен Telegram-бота |
| `ADMIN_IDS` | Список Telegram ID администраторов |
| `GOOGLE_CREDS_PATH` | Путь к JSON-ключу сервисного аккаунта Google |
| `GOOGLE_SHEET_ID` | ID Google Sheets-документа |
| `SMTP_*` | Настройки SMTP для отправки OTP |
| `ALLOWED_EMAIL_DOMAINS` | Разрешенные корпоративные домены |
| `DELETE_STATUSES` | Статусы, при которых сотрудник считается кандидатом на удаление |
| `DB_PATH` | Путь к SQLite-базе |

Секреты не должны храниться в документации, логах, публичных репозиториях или передаваться в чатах.

## 5. Локальное хранение данных

SQLite-база хранится на сервере в Docker volume: `./data/bot.sqlite3`.

Таблицы:

| Таблица | Данные | Назначение |
|---|---|---|
| `settings` | key/value служебные настройки | Хранение технических курсоров, например `healthcheck_cursor` |
| `managed_chats` | `chat_id`, `title`, `chat_type`, `approved`, `is_active`, `approved_by`, `updated_at` | Список групп, где бот approved/ignored и состояние активности |
| `chat_members` | `chat_id`, `user_id`, `username`, `full_name`, `last_seen_at` | Локальный индекс участников, используется как служебная таблица |
| `observed_chat_users` | `chat_id`, `user_id`, `username`, `full_name`, `first_seen_at`, `last_seen_at`, `last_alerted_at` | Пользователи, замеченные в approved-группах, для daily alert |
| `deletion_log` | `created_at`, `email`, `telegram_id`, `chat_id`, `result`, `reason` | Журнал попыток удаления пользователей |

Бот не сохраняет текст сообщений пользователей в SQLite.

## 6. Обрабатываемые персональные данные

| Категория данных | Где используется | Где хранится |
|---|---|---|
| Telegram ID | Регистрация, удаление, алерты, админ-доступ | Google Sheets, SQLite |
| Telegram username | Регистрация, алерты, отчеты | Google Sheets `Registration`, SQLite |
| Telegram full name | Регистрация, алерты | Google Sheets `Registration`, SQLite |
| Корпоративная почта | Регистрация, ручное удаление, журнал удалений | Google Sheets, SQLite `deletion_log` |
| ФИО сотрудника | Чтение из HR-листа | Google Sheets |
| Статус сотрудника | Автоудаление | Google Sheets |
| Названия и ID Telegram-групп | Управление группами и отчеты | SQLite |
| OTP-код | Подтверждение email | Временное in-memory состояние процесса, email-сообщение |

Содержимое сообщений в группах не сохраняется. При наблюдении активности бот использует только Telegram-метаданные отправителя и группы.

## 7. Функциональная логика

### 7.1. Регистрация пользователя

Триггер: пользователь отправляет `/start` боту.

Flow:

1. Бот очищает текущее FSM-состояние пользователя.
2. Бот проверяет, есть ли Telegram ID пользователя в листе `HQ E - COM`, колонка `ТГ`.
3. Если Telegram ID найден, бот отвечает: `Вы уже зарегистрированы ✅`.
4. Если Telegram ID не найден, бот запрашивает корпоративную почту.
5. Бот проверяет формат email и домен из `ALLOWED_EMAIL_DOMAINS`.
6. Бот генерирует 6-значный OTP и отправляет его по SMTP.
7. OTP хранится во временном in-memory FSM-состоянии.
8. Пользователь вводит OTP.
9. Если код корректный и не истек, бот записывает или обновляет строку в `Registration`.
10. Бот сообщает об успешной регистрации.

Ограничения:

- время жизни OTP: `OTP_TTL_SECONDS`, в production 600 секунд;
- количество неверных попыток OTP: 2;
- при `/start` бот проверяет только `HQ E - COM`.`ТГ`;
- при `/start` бот не сверяется с `Registration` и `Список Диёр`.

### 7.2. Подключение группы к управлению

Триггер: боту выдали права администратора в Telegram-группе.

Flow:

1. Telegram присылает событие `my_chat_member`.
2. Бот отправляет администраторам из `ADMIN_IDS` запрос на активацию группы.
3. Администратор выбирает `Да` или `Нет`.
4. Если выбран `Нет`, группа сохраняется как ignored.
5. Если выбран `Да`, группа сохраняется как approved.
6. Бот проверяет, есть ли у него права администратора и право ограничивать участников.
7. Если права достаточны, группа становится `approved + active`.
8. Если прав недостаточно, группа остается `approved`, но `inactive`.

Бот работает с группой только после явного approve администратора.

### 7.3. Healthcheck групп

Периодичность: `CHAT_HEALTHCHECK_INTERVAL_MIN`, в production 10 минут.

Flow:

1. Бот берет approved-группы из `managed_chats`.
2. Обрабатывает batch размером `CHAT_HEALTHCHECK_BATCH_SIZE`, в production 100.
3. Проверяет, находится ли бот в группе и есть ли у него нужные права.
4. Обновляет `is_active`.
5. Хранит курсор обработки в таблице `settings`.

### 7.4. Наблюдение пользователей в approved-группах

Триггеры:

- обычное сообщение в группе;
- появление новых участников в `new_chat_members`;
- callback-нажатие в группе.

Flow:

1. Бот получает Telegram-событие.
2. Проверяет, что чат является группой или супергруппой.
3. Проверяет, что группа approved.
4. Проверяет, что пользователь не является ботом.
5. Сохраняет или обновляет запись в `observed_chat_users`.

Сохраняемые поля:

- `chat_id`;
- `user_id`;
- `username`;
- `full_name`;
- `first_seen_at`;
- `last_seen_at`;
- `last_alerted_at`.

Бот не сохраняет текст сообщения, вложения, реакции или содержимое callback.

### 7.5. Daily alert по незарегистрированным пользователям

Периодичность: `UNKNOWN_SCAN_INTERVAL_HOURS`, дефолт 24 часа.

Flow:

1. Бот читает сотрудников из `HQ E - COM`.
2. Формирует список известных Telegram ID из:
   - `HQ E - COM`, колонка `ТГ`;
   - `Registration`, колонка `telegram_id`;
   - `Список Диёр`, колонка `E`;
   - `ADMIN_IDS`.
3. Бот проходит по approved + active группам.
4. Для каждой группы берет последних наблюдаемых пользователей из `observed_chat_users`.
5. Если `user_id` не найден среди известных ID, пользователь считается незарегистрированным.
6. Бот проверяет `last_alerted_at`.
7. Если по пользователю не было алерта за последние 24 часа, бот добавляет его в сообщение.
8. Бот отправляет сообщение в ту же группу, где пользователь был замечен.
9. После успешной отправки обновляет `last_alerted_at`.
10. Старые наблюдения удаляются по `UNKNOWN_USER_RETENTION_DAYS`, дефолт 7 дней.

Лимит пользователей в одном алерте: `UNKNOWN_ALERT_MAX_USERS_PER_CHAT`, дефолт 20.

Если пользователь остается неизвестным, бот может повторно отправить алерт по нему после истечения интервала 24 часа, пока пользователь не появится в известных источниках или запись наблюдения не будет удалена по retention.

### 7.6. Автоматическое удаление сотрудников по статусу

Периодичность: `STATUS_SCAN_INTERVAL_MIN`, в production 60 минут.

Flow:

1. Бот читает лист `HQ E - COM`.
2. Группирует строки сотрудников по `telegram_id`.
3. Если у строки нет `telegram_id`, она не участвует в автоудалении.
4. Для каждого `telegram_id` бот проверяет все строки с этим ID.
5. Удаление разрешено только если во всех строках с этим `telegram_id` статус входит в `DELETE_STATUSES`.
6. Если хотя бы в одной строке с этим `telegram_id` статус не входит в `DELETE_STATUSES`, бот не удаляет пользователя.
7. Если `telegram_id` находится в `ADMIN_IDS`, бот не удаляет пользователя.
8. В рамках одного запуска один `telegram_id` обрабатывается один раз.
9. Бот проходит по approved-группам и пытается удалить пользователя.
10. Количество попыток ограничено `MAX_KICKS_PER_STATUS_RUN`, в production 250.
11. Результат записывается в `deletion_log`.

Примеры:

| Telegram ID | Статусы в HR-листе | Результат |
|---:|---|---|
| `123` | `УДАЛИТЬ` + `ОСТАВИТЬ` | Не удалять |
| `123` | `УДАЛИТЬ` + `УДАЛИТЬ` | Удалять |
| `456` | `УДАЛИТЬ` | Удалять |

### 7.7. Ручное удаление по email

Доступно только администраторам из `ADMIN_IDS`.

Flow:

1. Администратор отправляет `/admin` или текст `админ`.
2. Выбирает `Ручное удаление по почте`.
3. Вводит корпоративную почту.
4. Бот валидирует формат email.
5. Бот ищет первую подходящую строку в `HQ E - COM` по колонке `Почта`.
6. Если `telegram_id` не найден, бот сообщает об ошибке.
7. Если `telegram_id` найден, бот пытается удалить пользователя из approved-групп.
8. Бот отправляет администратору Excel-отчет `manual_delete_report.xlsx`.
9. Результат записывается в `deletion_log`.

Ручное удаление не проверяет статус сотрудника. Это административное действие по явному запросу администратора.

### 7.8. Механика удаления из Telegram-группы

Для удаления участника бот использует два вызова Telegram Bot API:

1. `ban_chat_member(chat_id, user_id)`;
2. `unban_chat_member(chat_id, user_id)`.

Так пользователь удаляется из группы, но не остается в постоянном бане.

Результаты:

| Результат | Значение |
|---|---|
| `kicked` | Пользователь удален; также используется, если Telegram сообщил, что пользователя уже нет в группе |
| `error` | Telegram API вернул другую ошибку |

Если Telegram сообщает, что пользователя уже нет в группе, бот пишет `result = kicked`, а в `reason` указывает `already_not_member`.

После успешного удаления бот удаляет пользователя из локального индекса `chat_members` и пишет запись в `deletion_log`.

### 7.9. Watchdog polling

Cron запускает `scripts/watchdog_polling.sh` каждые 5 минут.

Flow:

1. Скрипт вызывает Telegram `getUpdates?timeout=10` из контейнера.
2. Если Telegram возвращает `409 Conflict`, значит основной polling уже удерживается ботом и работает корректно.
3. Если `409 Conflict` не получен, счетчик ошибок увеличивается.
4. После 3 последовательных неуспешных проверок выполняется `docker compose restart bot`.
5. Результаты пишутся в `data/watchdog_polling.log`.

## 10. Меры ограничения доступа и минимизации данных

Реализовано в текущей версии:

- административные действия доступны только `ADMIN_IDS`;
- группа становится управляемой только после approve администратора;
- бот игнорирует пользователей-ботов при наблюдении активности;
- бот не сохраняет текст сообщений и вложения;
- OTP хранится во временном in-memory состоянии и не записывается в SQLite или Google Sheets;
- наблюдения неизвестных пользователей автоматически удаляются после retention-периода;
- Google service account подключается из файла, примонтированного в контейнер read-only;
- основной сервис запущен в Docker с `restart: unless-stopped`;
- отдельный watchdog проверяет polling и перезапускает контейнер при сбое.

| Объект | Состав | Где хранится/передается |

## 12. Retention

Текущая логика:

- `observed_chat_users`: автоматическая очистка записей, если `last_seen_at` старше `UNKNOWN_USER_RETENTION_DAYS`, дефолт 7 дней;
- `deletion_log`: автоматическая очистка не реализована;
- `managed_chats`: хранится до ручного изменения/удаления записи;
- `Registration`: хранится в Google Sheets до изменения или удаления владельцем таблицы;
- OTP: хранится только во временном состоянии процесса до истечения TTL, успешной регистрации, превышения попыток или сброса состояния.

Рекомендация для согласования: определить бизнес-срок хранения `deletion_log`, `Registration` и `managed_chats`, а также порядок удаления данных по запросу субъекта или при закрытии процесса.

## 13. Ключевые риски и рекомендации для ИБ/DPO

| Риск/вопрос | Рекомендация |
|---|---|
| В `.env` и `service_account.json` есть секреты | Ограничить доступ на уровне VM, не хранить в репозитории, настроить ротацию |
| В SQLite есть персональные данные и журнал удалений | Ограничить доступ к серверу и резервным копиям, определить retention |
| В Google Sheets хранится HR-информация и регистрационные данные | Проверить права доступа к таблице и сервисному аккаунту |
| Ручное удаление не проверяет статус сотрудника | Считать это привилегированным административным действием, доступ только `ADMIN_IDS` |
| Удаление из Telegram-групп является действием с последствиями | Сохранять `deletion_log`, контролировать `ADMIN_IDS`, проверять права бота |
| Telegram и SMTP являются внешними системами | Зафиксировать их как интеграции в реестре обработки/поставщиков |
| `deletion_log` не имеет автоочистки | Согласовать срок хранения и при необходимости добавить scheduled cleanup |
| Bot token и Google service account дают высокий уровень доступа | Настроить принцип минимальных прав, хранение секретов и процедуру инцидентной ротации |

## 14. Что бот не делает

- не читает историю сообщений;
- не сохраняет тексты сообщений;
- не анализирует содержимое переписки;
- не удаляет пользователя без Telegram ID в HR-листе в автоматическом flow;
- не удаляет администратора из `ADMIN_IDS`;
- не подключает группу к управлению без approve администратора;
- не отправляет мгновенный alert по неизвестному пользователю при каждом сообщении;
- не использует MTProto/userbot как обязательную часть текущего production flow.

## 15. Контрольные точки для согласования

Перед финальным согласованием рекомендуется подтвердить:

- владельца Google Sheets и перечень пользователей с доступом;
- владельца VM и перечень пользователей с SSH-доступом;
- допустимый срок хранения `deletion_log`;
- допустимый срок хранения регистраций в `Registration`;
- необходимость шифрования диска/backup на уровне инфраструктуры;
- процесс ротации `BOT_TOKEN`, SMTP-пароля и Google service account key;
- порядок обработки обращений сотрудников по удалению/исправлению данных;
- перечень групп, где боту разрешено быть администратором.
